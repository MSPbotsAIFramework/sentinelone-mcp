## Requirement understanding

One line: Let an AI agent manage EDR threats, isolate endpoints, and review detections through SentinelOne.

The ticket asks for three capabilities against one SentinelOne console: (1) managing EDR threats,
(2) isolating (and, implicitly, restoring) endpoints, and (3) reviewing detections. It links to
`https://conduit.wyre.ai/plugins/sentinelone` as a reference for what "SentinelOne integration"
usually covers; that page is a third-party catalog entry, not a spec, and is used here only as
context, not as a source of truth for what to build.

## Current state (every claim carries path:line)

by direct repo access (`mbp.py mcplock info --repo sentinelone-mcp` → `default_branch: main`), not
by name guessing; no other SentinelOne-named repo exists in the org (checked `sentinelone-mcp`,

## Product design

### Goals / Non-goals

**Goals**

- Add the ability to isolate (disconnect from network) and reconnect one SentinelOne-managed
  endpoint, identified by hostname or agent UUID, from the same connector that already reviews
  SentinelOne detections — so an operator or AI agent acting on a SentinelOne alert can contain
  the affected device without leaving the MSPbots Connector tool set.
- Let the AI agent resolve a device by a hostname fragment first (new `search_agents`), since
  "isolate endpoints" as asked is action-by-device, not action-by-arbitrary-filter.

**Non-goals**

- No bulk/mass isolation by an open-ended filter in this version — one agent per call. If a
  future ticket asks for "isolate every agent matching X", that is a new, separately-scoped
  capability.
- No new credential field, no new credential type, no OAuth. The two existing headers
  (console URL + token) are reused as-is.
- No in-repo approval/confirmation workflow before isolating a device. Which roles may call
  `isolate_endpoint` / `reconnect_endpoint` is controlled by the MSPbots Connector's existing
  per-role, per-tool allowlist (deny-by-default, confirmed platform-wide behavior — wiki:
  `ProductDocs/15-Capabilities.md § Connection forms`); this repo does not add a second
  authorization layer on top of it.
- No change to the SentinelOne console service-user's role from this code — tenants that want to
  use isolate/reconnect configure that once, in their own SentinelOne console (documented, not
  automated, by this ticket — see AC8).
- Not re-architecting the already-covered "review detections" / "manage EDR threats" read paths;
  they are unchanged.

### Acceptance criteria AC1..AC9

- **AC1** — Given valid SentinelOne credentials on a `/mcp` request, when the caller invokes
  `search_agents` with a hostname fragment, then the response lists matching agents (uuid,
  computer name, network status, site) as size-capped JSON, and an empty match list is a normal
  (non-error) result.
- **AC2** — Given a known agent UUID and credentials whose SentinelOne role allows it, when the
  caller invokes `isolate_endpoint`, then the target agent is disconnected from network and the
  tool returns a success result naming the agent and its new (transitional) network status.
  Calling it again on an already-isolated agent is a no-op, not an error.
- **AC3** — Given a previously isolated agent, when the caller invokes `reconnect_endpoint` with
  its UUID, then the agent is reconnected and the tool returns success with the new (transitional)
  network status.
- **AC4** — Given credentials whose SentinelOne role lacks permission to isolate/reconnect, when
  either tool is called, then the response is the same structured `unauthorized` error envelope
  every other tool in this repo already returns for a permission failure — not a stack trace, not
  the raw SentinelOne error body.
- **AC5** — Given an agent UUID that does not exist on the console, when `isolate_endpoint` or
  `reconnect_endpoint` is called, then the response is a `not_found` error envelope.
- **AC6** — Given a `/mcp` request missing the required console headers, when any of the 3 new
  tools is called, then the behavior is identical to every existing tool today: HTTP 401 /
  "Missing credentials" from `GatewayCredentialsMiddleware`, unchanged.
- **AC7** — Given two concurrent `/mcp` requests carrying two different tenants' console
  credentials, when both call `search_agents` / `isolate_endpoint` / `reconnect_endpoint` at the
  same time, then neither request's credentials or results are visible to the other (same
  per-request isolation guarantee already proven for existing tools).
- **AC8** — Given the README after this change, when a reader opens it, then: the Tools table
  lists `search_agents`, `isolate_endpoint`, `reconnect_endpoint`; the top-of-file description no
  longer states the server is unconditionally read-only; and the Authentication section states
  that these two action tools need a service-user role with SentinelOne's "Agents – Actions"
  permission, while every other tool still only needs the current viewer-level role.
- **AC9** — Given the MSPbots Connector's existing per-role, per-tool allowlist (deny-by-default),
  when a role has not been explicitly granted `isolate_endpoint` / `reconnect_endpoint`, then
  calls from that role never reach this server's tool code in the first place — a non-regression
  check that the 3 new tools are registered the ordinary way (`mcp.tool(...)`, same as every
  existing tool) and do nothing to bypass that platform-level gate.

### Open questions

- **Q1 (not blocking; proceeding on a stated assumption).** Will existing tenants' already-issued
  console tokens (created per the current README instructions, which ask for a "viewer-level
  role") be able to call isolate/reconnect at all? Assumption: most will not, until a tenant admin
  upgrades that service user's SentinelOne role — this is expected, not a defect, and is exactly
  what AC4's structured `unauthorized` response is for. Documented as an operational note in the
  README (AC8), not treated as a design blocker.
- **Q2 (not blocking; resolved by a design choice, not a guess).** Is the Data Lake "unified
  inventory" `item_id` (already exposed by `list_inventory_items` / `search_inventory_items`) the
  same identifier as the classic Agent `uuid` the actions API requires? Not documented as
  equivalent anywhere in `purple-mcp` or in SentinelOne's own API grouping (Data Lake vs. classic
  Management Console API are separate subsystems). Rather than assume they match and risk
  isolating the wrong device, the design adds a dedicated `search_agents` tool against the classic
  `GET /web/api/v2.1/agents` endpoint, which is documented to return the same `uuid` the actions
  endpoints accept. The dev leg's Self-test should confirm this against a real console before
  relying on it (see Test strategy / `.ac.json` TC-S1-001).

## Tech design

### Conclusion

Extend `MSPbotsAIFramework/sentinelone-mcp` (do not fork `purple-mcp`, do not create a second
repo) with a small classic-API client and three new MCP tools — `search_agents`,
`isolate_endpoint`, `reconnect_endpoint` — reusing the connector's existing per-request credential
plumbing, error-envelope shape, and tool-annotation pattern. No new dependency, no new credential
field, no DB.

### Where the current implementation lives

- `src/sentinelone_mcp/server.py:33-60` — header names, `INSTRUCTIONS` (claims read-only today),
  `create_mcp_server` / `register`.
- `src/sentinelone_mcp/server.py:81-132` — `GatewayCredentialsMiddleware`, builds per-request
  `purple_mcp.config.Settings` from headers, unchanged by this ticket.
- `src/sentinelone_mcp/purple.py:41-58` — contextvar bridge (`_settings_var`,
  `_load_base_settings` monkeypatch) that every tool call reads through `current_settings()`.
- `src/sentinelone_mcp/tools.py:39-49` (imports), `228-269` (`_run`, the per-tool call/timeout/
  error-envelope wrapper), `366+` (`register`, one block per tool). No `agents`/actions module
  anywhere in this file or in `purple_mcp.tools` (confirmed, see Current state).
- `src/sentinelone_mcp/_json.py:23,30,186` — `MAX_CHARS`, `dump_json_capped(data, max_chars=...)`,
  `error_envelope(code, message, retryable)`. Reused as-is.
- `README.md:6` (read-only claim), `93-115` (Authentication headers table + prose), `117-162`
  (Tools table) — all three need an update (Change list below).

### Option analysis

- **Option A — chosen: add a thin classic-API client inside this repo.** New module (e.g.
  `src/sentinelone_mcp/agents_api.py`) using the already-declared `httpx` dependency
  (`pyproject.toml:14`) to call `GET /web/api/v2.1/agents` and
  `POST /web/api/v2.1/agents/actions/{disconnect,connect}`, authenticated with
  `Authorization: ApiToken <token>` using the same raw token `purple.current_settings()` already
  carries. Three new `@mcp.tool()` wrappers in `tools.py`, following the existing `_run` pattern.
  Smallest surface, no new dependency, identical multi-tenancy story to every existing tool.
- **Option B — rejected: extend `purple-mcp` upstream, then bump the pin.** `purple-mcp` is
  SentinelOne's own open-source library; the vendor-mcp SOP is explicit that third-party / vendor
  repos are reference-only — "不 fork、不镜像、不直接改开源代码". Also makes this connector depend
  on an upstream change outside MSPbots' review, for a capability that has nothing to do with
  Purple AI / Data Lake (purple-mcp's actual scope).
- **Option C — rejected: a second repo (e.g. `sentinelone-actions-mcp`).** One vendor, one set of
  credentials, one Connector card — splitting it in two would show the same product as two
  separate connectors in the catalog for no technical reason, and `mcp-track.md` 2.1's own
  decision table says "existing repo, missing capability → extend it", not "spin up a new repo".

- **Reused as-is**: `httpx` (already a dependency — no new package); the per-request credential

  shape, no new error vocabulary); the `ToolAnnotations` pattern already used for the three
  existing constants.
- **New dependencies**: none.
- **New/changed API surface**: 3 new MCP tool names (`search_agents`, `isolate_endpoint`,
  `reconnect_endpoint`). No existing tool's name, parameters, or response shape changes.
- **In-scope cleanup**: none found. `tools.py` is a single, recently-built file with one purpose;
  no stale code, no unused imports, no dead config in the paths this ticket touches.
- **Follow-ups (out of scope — list for a separate ticket if requested)**: batch isolation (filter
  many agents at once rather than one UUID per call); folding `search_agents` into the existing
  inventory tools if SentinelOne ever documents the Data Lake inventory `item_id` and the classic
  Agent `uuid` as the same identifier (today they are not documented as such — see Open Question
  Q2).

### Data & API contract

**`search_agents`**
- Params: `computer_name: str | None` (substring match), `uuid: str | None`,
  `network_status: Literal["connected","disconnecting","disconnected","connecting"] | None`,
  `limit: int = 10` (1-100), `cursor: str | None` (the classic API's own pagination cursor).
- Calls `GET /web/api/v2.1/agents?computerName__contains=...&uuid=...&networkStatus=...&limit=...&cursor=...`.
- Success: capped JSON
  `{"agents":[{"id":"<uuid>","computerName":"...","networkStatus":"...","siteName":"...","osType":"..."}],"next_cursor":"..."}`.
  An empty `agents` list is success, not an error (AC1).
- Errors: `unauthorized`, `invalid_argument` (malformed filter / bad `network_status` value —
  rejected by FastMCP's own argument validation before any HTTP call, same as every existing
  `Literal`-typed parameter in this repo).

**`isolate_endpoint`**
- Params: `agent_id: str` (required, the classic UUID).
- Calls `POST /web/api/v2.1/agents/actions/disconnect` with body `{"filter": {"ids": [agent_id]}}`.
- Success: `{"agent_id": "...", "network_status": "disconnecting", "affected": 1}`. SentinelOne's
  disconnect is asynchronous (the agent transitions through `disconnecting` before reaching
  `disconnected`); the tool reports the transition it triggered, not a guaranteed final state —
  callers that need to confirm final status call `search_agents` again.
- Errors: `unauthorized` (403; SentinelOne's documented shape is
  `{"has_error":true,"error_response":{"errors":[{"code":4030010,"title":"Insufficient permissions"}]}}`,
  mapped the same way `_envelope_for` already maps other 403s), `not_found` (`affected: 0`,
  unknown UUID), `invalid_argument` (malformed UUID, rejected before the HTTP call).

**`reconnect_endpoint`**
- Mirrors `isolate_endpoint` against `POST /web/api/v2.1/agents/actions/connect`; success reports
  `network_status: "connecting"`.

**Auth**: identical headers already required today — no contract change
(`X-Purplemcp-Base-Url`/`X-S1-Console-URL`, `X-Purplemcp-Token`/`X-S1-API-Token`). The classic API
call uses `Authorization: ApiToken <token>` with the same raw token `server.py` already strips a
`Bearer `/`ApiToken ` prefix from before handing it to `purple-mcp` (`server.py:39,103`) — reused,
not re-parsed.

**Storage**: none — stateless connector, nothing persisted anywhere in this repo, unchanged.

**Backward compatibility**: purely additive. No existing tool's name, parameters, or response
shape changes.

### Key flow / sequence

1. Agent calls `search_agents(computer_name="web-7")` (or already has a UUID) → gets candidate
   agent(s) with their current `networkStatus`.
2. Agent calls `isolate_endpoint(agent_id=...)` → `agents_api.disconnect` → classic API call →
   success or error envelope.
3. Later, agent or an operator calls `reconnect_endpoint(agent_id=...)` to restore connectivity.
4. At every step, the unchanged `GatewayCredentialsMiddleware` (`server.py:81-132`) is what put
   this request's console URL/token into the contextvar the new tools read via
   `purple.current_settings()` — no new credential path is introduced.

### Non-functional

- **Multi-tenancy / isolation**: no new state anywhere; reuses the existing contextvar-per-request
  settings (`purple.py:41-58`), the same guarantee every existing tool already relies on and that
  `tests/test_middleware.py` already exercises. The dev leg's self-test must add a concurrent
  two-tenant isolate call to prove no cross-tenant leakage on the two new write tools specifically
  (AC7 / `.ac.json` TC-S1-008).
- **Idempotency**: `isolate_endpoint` / `reconnect_endpoint` are annotated
  `idempotentHint=True, destructiveHint=True` — calling isolate twice on an already-isolated agent
  is a no-op per SentinelOne's own action semantics, not an error (AC2).
- **Security**: this is the connector's first **write** capability — everything else is read-only.
  Credentials still never touch disk or logs (`GatewayCredentialsMiddleware` unchanged). The
  classic API token now needs a higher-privilege role for 2 of what will be ~36 tools; this must
  be called out loudly in the README (AC8) so a tenant does not unknowingly grant isolate/
  reconnect by reusing a broadly-scoped ops token. Authorization of *which roles* may call these
  two tools stays entirely in the MSPbots Connector's own per-role, per-tool allowlist
  (deny-by-default, confirmed platform-wide — wiki `ProductDocs/15-Capabilities.md`); this repo
  adds no second authorization layer, consistent with the vendor-mcp SOP's "credentials only from
  headers, no token escalation" rule.
- **Logging**: no new log fields beyond the existing `tool=... outcome=... ms=...` line
  (`tools.py` inside `_run`); the target `agent_id` of a destructive call is not written to this
  service's own logs (the Connector's platform-level audit log already records who called which
  tool, when — wiki `ProductDocs/15-Capabilities.md § Why Connector`).
- **Performance**: classic API disconnect/connect calls are ordinary synchronous HTTP; reuse the
  existing `CALL_BUDGET_SECONDS = 100.0` budget (`tools.py:159`). No new load-bearing path in
  MSPbots' own infrastructure is introduced (all traffic is this connector calling SentinelOne's
  console directly), so no separate performance test case is written — this decision is deliberate,
  not an oversight.

### Rollout & rollback

Additive-only change, no feature flag needed. Ships the same way every MCP ticket does: merge to
`main`, publish to INT. Rollback = revert the merge commit; nothing persisted to undo. A tenant's
need to upgrade their SentinelOne service-user role is a one-time, tenant-side configuration step
(documented in the README), not something this code can or should automate, and not a rollback
concern.

### Test strategy

- Unit: `agents_api.py` functions against a mocked `httpx` transport — 2xx, 403, 404, timeout.
- Unit: the 3 new tool wrappers in `tools.py` for envelope mapping (missing credentials → 401,
  403 → `unauthorized`, 404 → `not_found`, malformed argument → `invalid_argument` rejected before
  any HTTP call).
- Concurrency: extend the existing per-request-isolation test style
  (`tests/test_middleware.py`) to cover the two new write tools specifically.
- Against a real console (not available to this pipeline): the full isolate → verify-via-search →
  reconnect round trip, and the 403 case against an actual viewer-level token. These are marked
  "needs a real vendor account" in `.ac.json` and do not block `6b`/`6c` per
  `references/mcp-track.md` §3 ("没有测试账号不算阻塞").

### Effort & breakdown

Single cohesive change in one repo, one PR: `agents_api.py` (new) + 3 tool wrappers +
`INSTRUCTIONS`/README updates + unit tests. Roughly half a day for one developer; no sub-task
split needed.

### Risks & dependencies

- **Risk**: some SentinelOne deployments split the classic Management API and the Data Lake
  GraphQL API across different base URLs (region-specific consoles). Mitigation: reuse the same
  `console_base_url` the existing read tools already use; if it is ever wrong for a given tenant,
  `search_agents` will surface a `not_found` / `upstream_error` envelope rather than silently
  isolating the wrong console — call this out in Self-test rather than assume it.
- **Risk**: Open Question Q2 (inventory `item_id` vs. classic `uuid`) — mitigated by design: a
  dedicated `search_agents` tool is added instead of reusing the inventory tools for the write
  path.
- **Dependency**: none on another ticket.
